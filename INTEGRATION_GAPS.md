# Integration gap review and bundled fix

Repository reviewed at `main` commit `fb9c1cd9baee3a9d225ebaa416ceb9d358159c02`.

## What was disconnected

1. **Orbital simulation did not produce the contact-plan contract used by routing.**
   `src/model/network.py` emits sampled positions and instantaneous satellite links; `src/routing/temporal_baseline.py` consumes time-windowed `Contact` records. No adapter joined those shapes.

2. **The fixed 14-node RL topology was not represented by the physical simulator.**
   The RL policy assumes node 0 = science, 1..8 = LEO, 9..10 = GEO, 11..13 = ground. The orbital simulator accepts an arbitrary undifferentiated satellite list.

3. **Ground stations were not first-class routing nodes.**
   The physical track used ground points for coverage scoring, while the routing/RL tracks used three destination node IDs. The mock RL graph explicitly omitted science-to-ground links, so direct-to-ground could not be evaluated.

4. **The RL environment was still fed by a random mock contact graph.**
   This made RL-vs-baseline comparisons useful for algorithm development, but not an end-to-end test of the orbital scenario.

5. **There are duplicate `Contact`, bundle, and earliest-arrival implementations.**
   `RL/rl_env_v0/src/rl/mock_graph.py` defines its own contact/bundle shapes and `eval_with_baseline.py` reimplements the baseline because the repository has two packages named `src`. That creates drift risk at exactly the policy/simulator boundary.

6. **Contact capacity was checked but not reserved.**
   Two independently routed bundles could both be told that the same future contact had enough residual capacity.

7. **Link bandwidth units were not a single contract.**
   The temporal router uses bits/second, while the packet simulator treats `Satellite.link_bandwidth()` as a per-frame byte budget. Mixing those values directly would create silent scale errors.

8. **The packet simulator did not carry science value/deadline semantics.**
   It routes generic 1 KB packets with per-frame BFS/greedy strategies, while the AI/routing problem is defined in terms of large `DataBundle`s with priority and deadlines.

9. **`config/prototype.yaml` was empty.**
   There was no executable source of truth for the fixed node roles, orbit assumptions, three ground stations, link rates/ranges/reliability, or traffic generation.

10. **There was no single experiment entry point across physics -> contacts -> traffic -> baseline/RL -> metrics.**
    Results were generated by separate scripts, so scenario parity depended on each script maintaining the same assumptions.

## What this bundle adds

- `src/integration/scenario.py` — creates the fixed 11 spacecraft mapped to RL node IDs and runs the existing orbital propagator.
- `src/integration/contact_plan.py` — converts sampled physical positions into directed temporal contacts, including three real destination node IDs and direct science-to-ground windows.
- `src/integration/capacity.py` — a reservation ledger that prevents future contact capacity from being double-booked.
- `src/integration/rl_bridge.py` — reproduces the frozen 158-feature / 14-action policy interface directly from the canonical contact plan, so existing MaskablePPO checkpoints can be evaluated without importing the second `src` package.
- `src/integration/simulation.py` — executes baseline and RL+deterministic-fallback policies against independent capacity ledgers built from the same physical plan.
- `src/integration/traffic.py` — deterministic priority/deadline-aware bundle generation shared by both policies.
- `config/prototype.yaml` — executable prototype assumptions (stored as JSON syntax, which is valid YAML 1.2, so no PyYAML dependency is required).
- `run_integrated_demo.py` — one command for the complete pipeline and CSV/JSON output.
- `tests/test_integration.py` — contract tests for direct-to-ground, capacity reservation, the 158-feature RL interface, and end-to-end routing.
- `.github/workflows/integration.yml` — CI for the routing and integration contracts.

## What still needs empirical work

The bundle connects the software, but two model-quality items should not be overclaimed:

- Existing PPO checkpoints were trained on the mock contact distribution. They can now be **evaluated** on physical contacts, but a strong final model should be retrained or fine-tuned on physical contact plans generated by this adapter.
- Weather, health, and battery are not yet driven by time-series telemetry. Weather/reliability come from the scenario config; queue pressure is derived from actual contact utilization; health/battery use configured defaults. The policy contract is ready for a future telemetry provider without changing the checkpoint interface.
